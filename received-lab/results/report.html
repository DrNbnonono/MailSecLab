结论

  • hopcount 计数与 Postfix 拓扑严格耦合：边界出现在「伪造 N + 真实跳数 = limit」处，且随 limit 线性缩放（50→47/48/49 三段式；8→5/6/7）。
  • 拒绝位置随剩余 hops 逐级后移：N=47 时 P3 拒绝并由 P2 生成退信（DSN 进 Mailpit）；N=48 时 P2 拒绝 P1 退信；N≥49 P1 在 DATA 阶段直接 554。

8 · 核心结论

已证明

  • Phase 1：Hop count ≠ header complexity；边界三段式（DATA 554 / 跨节点退信 / 投递）随 limit 线性缩放。
  • Phase 2：Postfix 的 loop 控制视图与消息头结构是两个独立维度；重复字段/Resent/ARC-style 不触发任何限制。
  • Phase 3A：ET050 现象是版本演化中的兼容行为（fix_quietly），3.11.6 提供了 add_header / reject 两种收紧策略。
  • Phase 3B：MTA 差分存在且可复现——头/体边界与畸形头拒绝策略均为实现相关。
  • Phase 3C：message interpretation is not a property of the byte stream alone——取决于解析器与信任边界。
  • E 系列：数量上有界（50/30/100，三种触发模式），字节上近乎无界（Postfix 9.09MB 头块 hopcount 失明通过），且存在 transport 盲 / parser 明的隐藏通道与 ~24× DSN 放大。
  • F 系列：字节通道下游解析代价可忽略（rspamd 正常）；WSP 通道宽度 = 连续无计数 MTA 跳数（改写归因见 G3：PF/OSMTPD 改写、Exim 只计数）；数量/字节上限均为配置常数；DSN 放大率 31.9×→1。

9 · 下一步实验方向（围绕核心问题：Received 能否无限制增长）

研究主轴确定为：邮件传输过程中 Received: 头能否无限制增长。目前已证明的是「Postfix 链内存在数量上限（hopcount=50）且数量与字节解耦」，但 FC500（5×90KB=450KB 头块投递）、OpenSMTPD 对 47 条无压力、ET050 计数盲区说明真实的限制面远比 hopcount 宽松。下一步用五个实验把「限制面」完整测绘出来。

E1 · 数量上限测绘：每个 MTA 的 Received 实际天花板

  • 同一 N 递增 corpus（N=0–120）分别打进 PF37 / PF11 / Exim 4.96 / OpenSMTPD 6.8 / Mailpit，二分定位每台 MTA 的实际拒绝/截断/无上限边界。
  • 已知锚点：Postfix hopcount=50（N≥49 DATA 554）；Exim 存在 received_headers_max（默认 50，行为待实测：拒绝、丢弃还是放行）；OpenSMTPD 3B 中 47+2 条无任何压力（上限待测）；Mailpit 未测。
  • 产出：MTA × 数量上限矩阵 —— 回答「链式传输中存在不存在没有数量上限的中继」。

E2 · 字节上限测绘：总头块能不能涨到 MB 级

  • 折叠 90KB Received × N（N=1–120）逐台 MTA 扫描：已知 header_size_limit(100KB) 只作用于单个头（FC500 证明 450KB 头块投递），总头块的真实上限是 message_size_limit（Postfix 默认 10MB）还是 cleanup 阶段的其它阈值，待实测。
  • 同步记录：每跳 prepend 后的报文尺寸增长曲线、超限时的具体表现（截断 / 554 / 静默丢头）。
  • 产出：单 MTA 总头字节天花板 + 尺寸增长曲线 f(N) —— 回答「Received 字节数能否涨到 hopcount 无法表达的量级（~10MB）」。

E3 · 计数盲区扫描：绕过计数但仍被下游视为 Received 的形式

  • 把变体集合（rEcEiVeD / Received :(WSP) / Received: / Receíved / X-Received / Resent 块）× N=60–100 在每台 MTA 上跑，判定各 MTA 对每种形式「计数 / 不计数 / 拒绝」。
  • 对每个通过者，用 Phase 3C 的三个 parser（Python email / Node mailparser / Go net/mail）判定下游是否把它解释为 Received —— 重点是 ET050 型：transport 计数失明但 parser 仍视为头的「隐藏增长」集合。
  • 产出：盲区矩阵（形式 × MTA × parser） —— 回答「存在多少条 hopcount 看不见的增长通道」。

E4 · 异构链增长通道：让 Received 跨域继续涨

  • 把链路改造成异构多跳（如 client → OpenSMTPD → Exim → Postfix → Mailpit，以及反向），预置 46–60 条 Received 后过链，观察总数能否越过任一单点上限继续增长。
  • 关键问题：单点上限是不是「全局」上限？一台无上限的 OpenSMTPD 在链中是否成为增长通道；Postfix 在链尾是否用 554 终止一切。
  • 产出：跨域链增长曲线 —— 回答「真实互联网多域传输下，Received 是否事实上只受路径长度而非任何协议上限约束」。

E5 · 放大效应定量：loop / DSN 与大头的组合

  • loop_test.sh 参数化：预置头块大小（0/90KB/450KB）× loop 深度，测量队列字节、DSN 尺寸、投递时延曲线。
  • 已知：空头 loop 第 8 跳被 554 终止、DSN 自绕一圈后终结（Mailpit 零收到）；缺的是大头块参与时的放大率 f(limit, header_bytes)。
  • 产出：资源放大定量模型，作为「无限增长」研究的安全后果章节。

后续（依赖 E1–E4 结论）

  • Rspamd 信任边界实验保留，但定位改为「下游安全组件如何对待超长/盲区增长的 Received 链」（Phase 5）。
  • DKIM l= 标签与 E3 盲区的组合（签名覆盖字节与验证者解析字节的错位）作为可选深化（Phase 6）。
  • 工程清理：代理恢复后还原 digest pin（原值在注释中），本轮镜像 ID 已记于 result/phase3/env.json。

E 系列总结：回答「能否无限制增长」

  • 数量维度：不能无限 —— 三种 MTA 都有上限（50 / 30 / 100），但上限值与触发模式（内联 554/500 vs 先收后退信）完全不同；Mailpit 类存档组件无上限。
  • 字节维度：近乎可以 —— Postfix 的 hopcount 对字节完全失明，R3 证明 9.09MB 头块可在真实 Received 仅 4 条时通过；唯一约束是 message_size_limit（10MB）。
  • 盲区维度：存在通道 —— OpenSMTPD 对 WSP 冒号变体既不计数也不拒绝，且该报文在 Node mailparser 眼里是 102 条 Received：一条「transport 失明、下游可见」的通道。
  • 放大维度 —— Exim「先收后退信」和 loop-DSN 机制把拒绝转化为放大；小报文 loop 场景 DSN 放大率 ~24×。

12 · G 系列 — 纠错与归因（2026-09-05 晚）

G 系列在验证 F 系列遗留问题时发现了语料生成器的双 CRLF 缺陷（折叠巨头首行后意外终结头块），据此撤回并重做了 F1 的 "rspamd 丢头" 结论与 R3 的字节通道机制，同时完成了 WSP 规范化的单头归因。完整纠错过程见 result/g-series/RECORD.md。

纠错摘要

  • 撤回：F1 的 "rspamd 把 9MB 头块整体丢弃（MISSING_*、score 10.4）" —— 该语料里头块在第一个巨头首行后即终结，"(AAA…" 是正文，rspamd 的解析是对的，三个 parser 也与它一致。
  • 修正：用修复语料重测 —— rspamd 对 9.07MB 真折叠头块 56ms · 3.4 分 · 无 MISSING；三个 parser 同样正常。不构成 parser 差分，也不构成 DoS 面。
  • 修正：R3 字节通道机制描述 —— 重做后确认真折叠头块 9,096,191B 过三跳链、Received 恒 4（见 §10 修正版）。E2 的字节上限测量使用的是无缺陷语料（send_received.py），维持成立。
