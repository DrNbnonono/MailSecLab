1. The forensic-readiness gap

The information in the SMTP headers is stored in clear text. Therefore the information can easily be edited. The possibility that the mail headers could have been edited makes the information in the headers suspect. (Van Staden & Venter, ISSA 2010, §II-A)

The 2010 paper (a decade before Sanchez/Duan/Dong's empirical study and a decade before Chen/Paxson/Jiang's "composition kills") takes a different angle: instead of empirically measuring forgery, it proposes an extension to RFC 5322 that preserves forensic integrity of the Received: trace chain — even when MTAs do not implement the extension.

2. Augmented Received-token rule

The paper proposes two augmentations to the ABNF received-token rule in RFC 5322 §3.6.7:

received-token  = "from" " (word / angle-addr / addr-spec / domain) ";" hash
                 "by"  (word / angle-addr / addr-spec / domain) ";" hash

Where:

  • The first hash is SHA-1(sending_domain || DNS_A(sending_domain)).
  • The second hash is SHA-1(receiving_host_domain || DNS_A(receiving_host_domain)).
  • Both hashes are computed by the receiving host at the moment of reception and recorded in the email envelope (cleartext, but bound to the receiver's DNS view at that instant).

And the augmented Received rule requires exactly one Received-token per received header entry (to keep parsing simple and to make gap detection deterministic).

3. Gap detection algorithm

The algorithm walks the Received: chain from the most-recent (bottom) hop to the oldest (top) hop, comparing each hop's receiving host with the previous hop's sending host. If they match, the chain is "trusted"; if they don't, the chain has a gap (some intermediate MTA didn't add a Received: entry or didn't implement the augmentation).

  1. Store the received send-receive pairs from last entry to first in a queue.
  2. Remember the receiving host of the first entry in the queue.
  3. Look at the next send-receive pair. Compare sending host with stored receiving host.
  4. If equal: store receiving host in the proven list, continue.
  5. If not equal: store the receiving host in proven list, store sending host in gap list, set gap-found flag, continue.
  6. If next pair is null: end. If gap-found → "gap detected", else "no gap found".

Output: two lists.

  • proven list — SMTP hosts that wrote augmented Received: entries.
  • gap list — last-known hosts whose entries are missing.

4. SMTP trust network

Aggregating proven across many emails yields a trust network: the subset of MTAs that implement the augmentation. The paper proposes:

  • Assign a trust value to each MTA in the proven set.
  • For an email whose full chain is in the proven set, propagate trust to the message.
  • Use the trust value to allocate anti-spam scan depth: high-trust messages get cheaper scanning, low-trust get deep scanning.

Similarly, the gap list can be mined for chronic offenders — intermediate MTAs that repeatedly omit the Received: entry are candidates for reputation downgrades.

5. Position in the literature

Compared to Sanchez/Duan/Dong 2010 (empirical, content-of-the-Received-chain) and Chen/Paxson/Jiang 2020 (composition vulnerabilities that bypass SPF/DKIM/DMARC):

  • Sanchez 2010 measures what is actually in Received: chains; Van Staden 2010 proposes what should be added.
  • Chen 2020 shows why authenticated Received: data cannot be trusted at the parser-differential layer; Van Staden 2010's hash augmentation is orthogonal (it defends the envelope against honest but buggy gaps, not against intentional forgery).
  • Both are foundational for MailSecLab's H-series: H1 (FEMTA from FIMTA's trust boundary) is the practical realization; Van Staden's augmentation is the future integrity layer that would let us sign FEMTA provenance at scale.

6. How MailSecLab uses this paper

  • H1 (Received trust boundary): The current algorithm of parsers/h1_femta.py uses FIMTA stamp only. The proposed hash augmentation would let a server additionally stamp SHA-1(fimta_domain || dns-resolved-IP-at-arrival) into each Received: entry, so future MailSecLab runs can cross-check the original DNS view of the receiver against today's DNS to detect retroactively-tampered chains.
  • H3 (Received differential against composite message): Van Staden's gap-detection is the direct algorithmic ancestor of H3 — the same scan from last hop to first, compare receiving host of hop n with sending host of hop n-1 recipe is used in parsers/h3_received_diff.py.
  • Provenance tag in .eml archives: parsers/fingerprint_chain.py adds a X-MailSecLab-Provenance header to every archived mail containing the chain hash — this is the modern realization of Van Staden's proposed augmentation, recorded as additional header rather than extending the Received-token ABNF (which would break interop).
  • Trust assignment: The paper's SMTP-trust-network idea is the conceptual ancestor of the H-series trust score in received-lab/results/H3/trust.json: each hop is assigned a confidence based on (a) implementing the augmentation, (b) stable network identity, (c) historical FEMTA evidence.
  • Future work direction: Van Staden's idea of using the gap list to find chronic non-compliant MTAs maps directly to the parsers/gap_list_mining.py notebook — repeated gaps at the same provider IP can be used as a reputation signal even without authentication.
