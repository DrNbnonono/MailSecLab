1. Core thesis — composition kills

Component-based software design is a primary engineering approach for building modern software systems. This programming paradigm, however, creates security concerns due to the potential for inconsistent interpretations of messages between different components. In this paper, we leverage such inconsistencies to identify vulnerabilities in email systems. (Chen, Paxson, Jiang, USENIX 2020, Abstract)

The paper demonstrates 18 evasion exploits against the SPF + DKIM + DMARC authentication stack, tested against 10 popular email providers and 19 email clients (including web, Windows, macOS, Linux, Android, iOS). All tested systems proved vulnerable to at least one attack.

2. The four authentication stages

An email passes through at least six components before the user reads it:

  1. Sender MUA composes the message.
  2. Sender MTA (authenticated by user; signs with DKIM if configured).
  3. DNS — provides SPF / DKIM / DMARC records.
  4. Receiving MTA — runs SPF, DKIM, DMARC, anti-spam, anti-virus.
  5. Receiving MUA (web / desktop / mobile) — parses and displays.
  6. The user — must make a trust decision from the rendered output.

The paper's three attack classes exploit inconsistencies between these stages:

  • Intra-server (A1–A5): SPF, DKIM, DMARC, and DNS components inside one provider disagree.
  • UI-mismatch (A6–A13): the receiving MTA authenticates one From header, the MUA displays a different one.
  • Ambiguous-replay (A14–A18): A DKIM-signed email is replayed with additional forged headers or body content that passes verification.

3. Threat model

Three attacker types:

  • Forgery attacker — sends arbitrary emails from their own server, spoofing From to a legitimate domain.
  • Replay attacker — has a legitimately DKIM-signed email (advertisement, registration, mailing list) and replays it with crafted extras.
  • Account attacker — has a real account at the target provider; uses a custom MUA to bypass the provider's outbound From check.

Assumption: legitimate sites configure SPF/DKIM/DMARC correctly and strictly. The paper shows that even strict deployment is bypassable.

4. Intra-server attacks (A1–A5)

IDWhatAffected providers
A1 MAIL FROM is a non-existent subdomain (e.g. any@notexist.legitimate.com). SPF can't find a policy for it, so the verifier falls back to HELO. DMARC alignment then uses legitimate.com (from From) — pass. Several implementations that follow HELO fallback
A2 MAIL FROM contains an unclosed comment (e.g. (any@legitimate.com). SPF parser sees empty MAIL FROM → HELO fallback. DMARC parser sees legitimate.com from the comment → alignment OK. Tutanota, Protonmail, Zoho, Mail.ru and others
A3 NUL byte (\x00) inside the DKIM selector splits the DNS query. DKIM component asks for selector._domainkey.legitimate.com but the resolver truncates at the NUL and queries selector._domainkey.attack.com — attacker's key. Signature "verifies" with d=legitimate.com but uses attacker's public key. Gmail (fixed in 2020); exploitable when C-string semantics differ from Perl/Python semantics
A4 DKIM-Signature d=legitimate.com(.attacker.com — DMARC parser takes the part before ( as the domain, DKIM parser uses the full string to query the public key. iCloud, Zoho, Naver, Tutanota, Protonmail, Mail.ru
A5 MAIL FROM contains the SPF-injection trick: any@legitimate.com'@a.attack.com — the MTA's local parser sees a valid address under attack.com (so it accepts the SMTP dialog), but the SPF parser uses the first @ and queries legitimate.com. iCloud, Zoho, Tutanota, Protonmail, Mail.ru

5. UI-mismatch attacks (A6–A13)

The receiving MTA and the MUA disagree on which From: header to trust. The paper catalogues 8 distinct attack vectors:

IDVectorBehaviours
A6 Multiple From: headers 19/29 implementations accept. iCloud Web + Mail (Win) display the LAST; Mail (Mac) shows both; everyone else shows the FIRST. Server uses the FIRST for DMARC.
A7 Space-surrounded From: (e.g. From: …) 3 edge cases (leading, trailing, folding). Bypasses Mail.ru, rewrites in Fastmail forwarding, mis-parsed by Naver/Outlook.
A8 From alternative headers (Sender, Resent-From) 7 MUAs fall back to Sender/Resent-From when From is missing or unrecognised. All servers use From only.
A9 Multiple email addresses in one From 5 distinct behaviours: first / last / all / none. Tutanota Web shows last.
A10 Base64 / quoted-printable address encoding (e.g. From: =?utf-8?B?YWRtaW5AbGlnaXRpbWF0ZS5jb20=?=, <any@attack.com>) Yahoo, Outlook, iCloud, Fastmail, Zoho, Tutanota servers do not decode — they use attack.com for DMARC. Their web interfaces and most MUAs decode — they display admin@legitimate.com.
A11 Route portion (@a.com,@b.com:d@d.com) Fastmail Server ignores route; 10 MUAs also ignore → both show d@d.com as real address. The attack is when the server uses one portion and the client another.
A12 Quoted-pairs (\ escaping) Gmail + iCloud Web recognise escaped boundary; Mail (Win) + iCloud Server don't.
A13 Precedence of <> vs , Mail.ru/Zoho DMARC: < has higher priority → uses attack.com. Outlook (Win) + 8 others: , separator → uses legitimate.com.

6. Ambiguous-replay attacks (A14–A18)

IDWhat
A14 Incomplete h= list. Real sites sign only some headers (e.g. American Airlines: only h=from; Citi: h=from:subject). Attacker appends Content-Disposition to make the legitimate body render as an attachment.
A15 Multiple headers exploit: A site signs h=subject only. Attacker appends a new Subject: header. Server uses the original; MUA uses the appended one.
A16 Body spoofing via the l= tag. A site uses l=200 in DKIM-Signature so the body is only partially signed. Attacker appends a new multipart boundary, redefines Content-Type: to multipart/mixed with the new boundary, and places a malicious message in the "preamble" (which RFC 2046 says is not displayed). Real sites vulnerable: discover.com, baidu.com, akamai.com, manuscriptcentral.com, badoo.com, blizzard.com, Zoho.com.
A17 Provider-side From validation bypass. Attacker uses real account but sends with From: admin@legitimate.com\, <real_user@legitimate.com>. Provider checks the second address (matches authenticated user), DKIM-signs it. Receiver sees the first address. Fastmail accepts arbitrary domains; iCloud/Naver/Zoho accept multiple From and check the first; Gmail/Zoho/Mail.ru accept the quoted-comma form and only check the second.
A18 Two-step replay vs. provider's DKIM signature. (1) Attacker uses their own account to send a perfectly-formed email (with whatever content they want — but the From must match the account). (2) Attacker adds a second From: with the target's address and resends. Receiver's DKIM verifier uses the original From → passes DMARC alignment. MUA may use the second From.

7. Scope of the impact

10 email providers (Gmail, iCloud, Outlook, Yahoo, Naver, Fastmail, Zoho, Tutanota, Protonmail, Mail.ru) and 19 MUAs (Foxmail, Outlook, Thunderbird, eM Client, Apple Mail, GMail mobile, …) tested:

  • 6/10 providers were affected by intra-server attacks (Table 1).
  • All 10 providers were vulnerable to UI-mismatch attacks (Table 2).
  • All 19 MUAs were vulnerable to UI-mismatch attacks.
  • All providers were vulnerable to ambiguous-replay attacks (A18 specifically).

The paper also found that the open-source tools Postfix, OpenDKIM, OpenDMARC and postfix-policyd-spf (Python) all had at least one implementation inconsistency that contributed to the attacks above.

8. Disclosure & mitigations

All findings reported to vendors and to CERT/CC. Outcomes:

  • Gmail — fixed A3 and A18 immediately, paid two cash rewards.
  • Zoho — confirmed and mitigated, four bounty rewards.
  • Protonmail / Mail.ru / Naver / Fastmail / eM Client / iCloud / Tutanota / Thunderbird — acknowledged and engaged on fixes.
  • Microsoft — disregarded the report (viewed as "social engineering").
  • Yahoo — misunderstood the report; no further reply.

Recommended mitigations from the paper:

  1. DKIM oversigning — sign the same header twice (h=from:from:subject:subject:to:to:...) and sign non-existent headers (h=subject for messages without one). Only Yahoo adopted this.
  2. No l= tag — sign the entire body, or none of it.
  3. Display authentication results in MUAs — most don't show SPF/DKIM/DMARC status to the user.
  4. Strict From-header validation at send time — Outlook already does this; only Naver's case remains.
  5. Push auth status via IMAP extension (proposed by eM Client) — instead of relying on the MUA to re-parse, have the server report its own verified identity.
  6. Type systems — pass typed data between internal components so "data" cannot be confused with "control" (the A4 / A5 root cause).

9. How MailSecLab uses this paper

  • K-series (DKIM verifier differential): A3, A4, A15, A16, A18 are the canonical "DKIM parser differential" probes. Our K1–K13 matrices (covering OpenDKIM, dkimpy, Python's email DKIM, Perl Mail::DKIM::Verifier, rspamd, and the bundled opendkim) are direct re-tests of A14–A16 against current software.
  • F-series (parser differential): A6–A13 are the From-header versions of Andarzian 2025's D1–D15. We use Chen 2020's attack list (the simpler, classical "A1–A13" alphabet) as the F-series baseline; the more recent D1–D15 are the F2 extensions.
  • I-series (forged Received chains): A18's "replay with extra From" is the basic primitive of our I2 self-consistent forged chain generator. A16's l= body-spoof is the basis for I3 "body smuggling".
  • espoofer (the authors' open-source tool) is incorporated as parsers/espoofer.py in MailSecLab for replaying the 18 attack vectors against new providers.
  • DNS-validation logic: A3 / A4 / A5 are precisely why parsers/dkim_dns_chain.py validates DNS-query inputs defensively (rejects NUL, splits on ( / @ / control characters, etc.).
