1. Threat model & idea

An email is parsed at least three times: by the receiving MTA, by the spam/virus filter(s), and by the mail client. Any differential in interpretation creates a window for smuggling: the filter sees one thing, the client sees another, and the malicious payload slips through.

Differentials in how systems parse data (a.k.a. parser differentials) occur when different systems (such as virus filters, spam filters, or mail clients) interpret the same email message differently. These differentials can create security gaps that allow malicious content to slip through undetected by one component but processed by another. (Andarzian et al., 2025, §I)

Previous work (Chen 2020, Longin/SEC Consult, Müller, Poddebniak) all relied on manual analysis. This paper is the first to apply differential fuzzing to MIME parsers at scale, combining:

  • AFL++ — coverage-guided grey-box fuzzer (instrumented C targets).
  • T-Reqs — grammar-based black-box fuzzer; better at semantic header confusion.

2. Fuzzer setup (AFL++ + T-Reqs)

Targets

ProjectVersionLanguageFunction
Postfix3.8.2CMail server
SpamAssassin4.0.0PerlSpam filter
ClamAV1.2.0CVirus filter
Evolution3.50.0CMail client (reference)

All four are already enrolled in OSS-Fuzz — the paper finds that even OSS-Fuzz's harnesses are inadequate.

Pipeline

  1. Generate / mutate MIME messages.
  2. Feed identical input to all four targets.
  3. Capture each target's parsed output (ASCII rendering of the MIME tree).
  4. Diff Evolution's output (the user-visible result) against each filter's output. If they disagree, mark as a parser differential.
  5. Corpus-minimise using AFL++'s afl-cmin to keep only the uniquely-differing test cases.

Findings per fuzzer

  • AFL++: 448 unique test cases (Crash-free differentials). Many bias toward ClamAV + Postfix because both are instrumented; SpamAssassin (Perl) is opaque.
  • T-Reqs: 349 unique test cases after minimisation. Far better balance across SpamAssassin, ClamAV, and Postfix.
  • Both: many memory-corruption bugs in Postfix, ClamAV, Evolution — OSS-Fuzz should have caught these, but did not.

3. Results — 448 + 349 differentials

Even when only looking at output equality (ignoring crashes), there are hundreds of distinct MIME inputs that filter and client disagree on. The paper then manually reduced this to 15 root causes.

5. Exploitable differentials (D3, D4, D11)

Of the 15 root causes, three are exploitable in the test setup (Postfix + SpamAssassin + ClamAV → Evolution / Thunderbird):

DifferentialSmuggling targetRecipe
D3 SpamAssassin (bypasses for Evolution & Thunderbird) Send Content-Transfer-Encoding: base64 first, then Content-Transfer-Encoding: 7bit; put the GTUBE spam-test value in the body. SpamAssassin reads the second header (7bit, raw text), so it doesn't decode GTUBE — but Evolution/Thunderbird read the first (base64, decoded) and display the spam payload.
D4 SpamAssassin (bypasses for Evolution & Thunderbird) Two Content-Type headers: first text/plain, then multipart/alternative; put GTUBE inside a multipart preamble. SpamAssassin uses text/plain and sees nothing spammy; the multipart-aware clients use the second header and render the preamble (which contains GTUBE).
D11 SpamAssassin (bypasses only for Evolution) Send Content-Transfer-Encoding:: base64 (extra colon). SpamAssassin rejects the entire header so it doesn't decode the body. Evolution is more lenient and still base64-decodes, showing the GTUBE payload. Thunderbird also rejects the header, so the bug is Evolution-specific.

None of the D1–D15 differentials could be used to smuggle past ClamAV in the tested setup — ClamAV's "decode anyway" behaviour ends up making it the most defensive of the four. But the paper notes that test value limitations (EICAR must not have extra data at the start) leave three D's (D5, D7, D9) marked "Unknown".

6. How MailSecLab uses this paper

  • F-series (parser differential matrix): D1–D15 is the canonical differential matrix between Postfix, OpenDKIM, rspamd, ClamAV-style filters, and mailsec's reference client. We extend D1–D15 with M-series findings (parser-friendly SMIME, DKIM canonicalization) when running F2 across the 13 mail utilities installed in received-lab/tools.
  • AFL++ + corpus minimisation pipeline: Adopted as the standard harness in parsers/. The harvested differentials/*.eml corpus is the seed corpus for every new parser we add.
  • D7 / D11 / D12 / D14 (Evolution↔Thunderbird client mismatches): Define F3 (mail client rendering mismatch). When comparing parsers/python-eml-parser output against parsers/perl-mail-dkim, every finding is now classified by which D# it matches.
  • Memory-corruption bugs in OSS-Fuzz-enrolled targets: This paper's findings imply OSS-Fuzz harnesses for ClamAV/Postfix/Evolution are weak. MailSecLab reports new fuzz harnesses (see parsers/fuzz_harness/) that cover IMF parsing, not just MIME — extending the paper's scope.
  • Defense implication for L2 (DKIM canonicalization differential): D5 (per-line vs whole-body base64) and D1 (Postfix never base64) are exactly what K2 (DKIM verifier differential) probes measure.
  • Future work the paper explicitly identifies: IMF and SMTP parser differentials, S/MIME differential fuzzing. MailSecLab's planned F4 (IMF) and F5 (SMTP DATA command shape) directly continue this line.
