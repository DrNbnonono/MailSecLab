1. The SMTP smuggling threat

SMTP smuggling was introduced by researchers of SEC Consult in December 2023. This attack exploits the inconsistent processing of SMTP commands between the sending and receiving MTA servers. The key idea is to embed SMTP commands into the body of an email, tricking the receiving MTA into misinterpreting the data (email body) as code (SMTP command). (Wang et al., USENIX 2025, §2.3)

Three conditions for a successful smuggling

  1. The sender MTA passes through one of the 13 known end-of-data variants (A1–A13) including bare \n.\n, \r.\r, \r.\r\n, and the seven \x00-trailing variants.
  2. The receiver MTA accepts that variant as the actual DATA terminator.
  3. SMTP command pipelining is enabled, so the receiver treats the remaining bytes as a new mail transaction.

The 13 payloads (Table 1)

IDPayloadIDPayload
A1\n.\nA8\n\x00.\n
A2\n.\rA9\n\x00.\r
A3\r.\nA10\r\x00.\n
A4\r.\rA11\r\x00.\r

A6\r.\r\nA13\r\x00.\r\n
A7\r\n\x00.\r\n

A7–A13 are new payloads introduced by this paper. The \x00-trailing variants target C-string semantics, where strchr(s, '\x00') terminates processing prematurely.

2. Public services — 19/22 exposed

Receiving side (Table 2)

8/22 public providers accept at least one smuggling payload:

  • Sina, Sohu, Yandex: vulnerable to A1, A5 etc.
  • Fastmail: vulnerable to A4, A6, A10, A12 (has some mitigations).
  • Cock.li, Daum.net, Rambler.ru: multiple A's.
  • Mail.ru, 163.com truncate the smuggled body (still a partial finding).
  • Sina displays the smuggled email and drops the legitimate first one (worst case).
  • Gmail, Yahoo, Outlook, iCloud: not vulnerable on receiving.

Sending side (Table 3) — much worse

18/20 providers transmit the smuggled payload unfiltered. Notable observations:

  • Gmail, Yahoo, Zoho, AOL: vulnerable to all of A8–A13 (the \x00-trailing ones) because they treat \x00 as a string terminator.
  • Outlook uses "sender checking" on the second email, but still lets the original content pass for A6–A12.
  • Fastmail not only fails to filter but actively splits the email into multiple parts — turning it into an email relay usable for spam or bombing.
  • 163 sending-side: vulnerable via dot-stuffing bypass.
  • Mail.ru, iCloud implement "string filtering" (extra spaces around \n / \r) — but these do not cover the \x00 cases.

4. Private services — 1,577/6,917 exposed

Three methodologies for ethically testing private mail:

User study (48 universities)

  • IRB-approved; participants send back what they see in their inbox.
  • 23/48 receiving-MTAs vulnerable. A1 and A5 are the most effective.
  • U15 (Cisco) and U48 (AU) vulnerable to all 13 payloads.
  • The dominant underlying infrastructures: Proofpoint (8 vulnerable), Outlook (most patched), Postfix, AppRiver, Sendmail, Cisco, Mimecast.

DKIM side-channel

Encode "this is the second-half" via a second DKIM-Signature with a separate selector on a self-hosted DNS zone. Splitting the email into two splits the DKIM queries; the DNS log tells you exactly which test ID arrived.

Non-intrusive test

Place the SMTP smuggling payload inside a vulnerability-report email. If the receiver is vulnerable it splits the message and the vulnerability report gets delivered (with the attack delivery); if not, the SMTP session hangs waiting for \r\n.\r\n and you close after 10 seconds. No email is delivered to non-vulnerable services — essential for scale.

6. Mitigation

  • Receiving MTAs: standardise on the canonical \r\n.\r\n (RFC 5321 §4.1.1.4 explicitly warns against bare \n); disable SMTP pipelining for the time being (costs throughput).
  • Sending MTAs: encode the email body in base64 by default — this is the recommended fundamental fix per the paper. Python's smtplib already does this.
  • Workaround: dot stuffing + suspicious-string filtering (e.g. drop bare \n, \r, \x00). These block most of the known attacks but are not fundamental fixes.
  • Online detection service at smuggling.breakspf.cloud for self-diagnosis.

7. Disclosure

112 days from receipt of disclosure to paper submission; 1,713 replies (most auto-responses); 117 manual responses; 20 admins used the self-diagnosis tool. Outlook/Gmail/Yandex/Kakao/Fastmail/Zoho acknowledged; Yahoo/AOL/Sina did not respond. Postfix recommended cleanup_replace_stray_cr_lf + message_strip_characters. Axigen recommends "Body CR-LF correction" in web admin.

8. How MailSecLab uses this paper

  • I-series (I1 MTA differential). The 13-payload matrix A1–A13 is the canonical probe set for MailSecLab's parsers/smtp-smuggle.py parser. Every new MTA deployed in the lab is run against A1–A13 on both receiving and sending sides; results are tracked in parsers/results/smtp_smuggling.csv.
  • Postfix / Exim / Haraka / Axigen coverage: directly drives the version matrix we test against (3.5.8, 3.9.0; 4.97.0, 4.97.1; 3.0.3; 10.4.3, 10.5.25). The findings on a fixed Postfix ≥ 3.9.0 set the pass threshold for our container-baseline compliance.
  • Shared SPF / BreakSPF link: Wang's 81 k / 63 k shared-domain counts extend the F-series SPF-acceptance model with the new failure mode "the sender MTA is one of the 18 vulnerable outgoing MTAs". This becomes a feature in the H3 attribution pipeline.
  • 1,577 vulnerable private domains: serves as the seed-corpus for investigating how the user-study self-diagnosis method scales to bottom-up reputation inference on private email systems.
  • Pipelines-internal suggestion: the non-intrusive test pattern (test-payload inside the report, abort SMTP after 10 s if no 354) is the template we use when MailSecLab probes new private email services that have not been seen before.
